# AI HANDOFF — OJO DE DIOS

## Qué es Ojo de Dios

Ojo de Dios es una plataforma modular local de auditoría interna/laboratorio.

Debe construirse como:

- chasis profesional;
- panel web responsive;
- API preparada para Android;
- 16 módulos visibles;
- TechniqueRegistry;
- X5/OjoRouter;
- Mistral/LaIA;
- Hermes Agent Lab;
- EvidenceStore;
- ScoringEngine;
- VersionLock;
- Kill Switch;
- Demo mode;
- Windows first-run;
- Attack Surface Graph;
- Service Intelligence Graph;
- integración X4/X5;
- puntos exactos IMPLEMENTACION_USUARIO_REQUERIDA.

## Nota crítica — Módulo 12

El Módulo 12 ya fija la filosofía del proyecto: autonomía supervisada, no-code desde panel/app, LaIA/Mistral como cerebro táctico, X5 como ejecutor validado, Hermes Agent como constructor de laboratorio y DeepSeek como arquitecto avanzado. No recortar esta filosofía en rondas futuras.

## Nota crítica — Módulo 13 Android

El Módulo 13 Android ya tiene base documental hasta Vector 11 en `docs/techniques/13_ANDROID.md`: Vector 1 interfaz/USB Directo/Red Móvil, Vector 2 payloads, Vector 3 control remoto avanzado, Vector 4 ataque físico USB, Vector 5 Red Móvil/MITM, Vector 6 Análisis de Apps, Vector 7 IMSI Catcher/BTS/RF móvil, Vector 8 Servicio de Accesibilidad/Registro de Eventos, Vector 9 Capa de Conectividad, Vector 10 Carteras de Criptomonedas/Apps Financieras y Vector 11 Mensajería. En rondas futuras no resumir ni perder funciones; ampliar desde esa base sin borrar contenido existente ni afirmar ejecución si no existe implementación aprobada.

Mantener filosofía M12: LaIA dirige, X5 valida/ejecuta, Hermes Agent construye, DeepSeek diseña/revisa, y Policy Engine/Scope/Kill Switch/EvidenceStore/AuditLog gobiernan autorización, evidencia y cierre seguro.

## Política de tests dinámicos

Antes de crear o modificar tests de registry, técnicas, módulos, capabilities, wrappers, Hermes, panels, workers, EvidenceStore, X5/OjoRouter, Tool Adoption, CVE-to-Technique o Ransomware Resilience Lab, leer:

- [docs/DYNAMIC_REGISTRY_TESTING_POLICY.md](docs/DYNAMIC_REGISTRY_TESTING_POLICY.md)

Frase obligatoria:

“El registry de Ojo de Dios es dinámico. El número total de técnicas es una métrica informativa, no una condición bloqueante. Los tests validan invariantes y contratos de cada técnica registrada, no un conteo fijo.”

No crear tests bloqueantes por conteo exacto fijo. No fallar porque aparece una técnica nueva, un módulo experimental aprobado, una capability transversal o una proposal Hermes. Validar contratos, estados honestos, permisos, evidencia, ausencia de secretos, aprobaciones y carga por X5/OjoRouter.

## Roles principales

### X5 / OjoRouter

X5/OjoRouter es el motor de decisión y ejecución.

Debe:

- recibir objetivo;
- consultar TechniqueRegistry;
- validar permisos;
- crear plan;
- lanzar jobs;
- seleccionar worker;
- guardar evidence;
- actualizar scoring;
- decidir fallback;
- pedir análisis a Mistral;
- pedir evolución a Hermes si falta una pieza.

X5 no debe depender de la lógica interna de una técnica.
X5 debe trabajar por contratos.

### Mistral / LaIA

LaIA no es simbólica.

LaIA es el cerebro operativo con control.

Debe:

- interpretar intención;
- analizar dominio/IP/rango/URL/objetivo;
- planificar cadena de técnicas;
- rellenar parámetros;
- analizar evidencias;
- decidir fallback;
- cambiar estrategia;
- entender Attack Surface Graph;
- explicar en pantalla;
- redactar informes;
- devolver JSON validado.

LaIA no debe:

- ejecutar comandos libres;
- inventar técnicas;
- saltarse TechniqueRegistry;
- marcar stubs como operativos;
- ignorar IMPLEMENTACION_USUARIO_REQUERIDA.

Si el JSON de LaIA no valida, X5 no ejecuta.

### Hermes Agent Lab / Evolution Engine

Hermes no es módulo 17.

Hermes se integra principalmente en:

- Módulo 12 Orquestación X5 + IA + Hermes Agent Lab.
- Módulo 16 Ops / Evidence / Calidad.

Hermes sirve para:

- crear skills;
- crear wrappers;
- crear parsers;
- crear schemas;
- crear paneles de laboratorio;
- crear workers de laboratorio;
- crear fixtures;
- crear tests estructurales;
- proponer mejoras;
- proponer nuevas variantes;
- documentar cambios.

Hermes siempre sigue:

sandbox → tests estructurales → revisión Mistral → diff → aprobación usuario → promoción controlada

Hermes nunca debe:

- autoaprobarse;
- tocar producción sin aprobación;
- activar stubs como operativos;
- ejecutar acciones reales directamente;
- ocultar cambios.

## Handoff Módulo 16 — Estación LaIA/Mistral y Hermes Agent

LaIA/Mistral y Hermes Agent forman parte de la normalización documental inicial de M16:

- LaIA/Mistral se ejecuta localmente con Ollama y usa el prompt `docs/ai_prompts/laia_mistral_system_prompt.md`.

- LaIA no ejecuta comandos; interpreta intención, rellena contratos, analiza evidencias y solicita confirmación humana cuando corresponda.
- Hermes Agent usa DeepSeek como proveedor y el prompt `docs/ai_prompts/angel_hermes_system_prompt.md`.
- Hermes Agent trabaja únicamente en `modules/laboratory/` salvo aprobación explícita del operador.

- M16 debe preservar `storage/runtime/laia_mistral_status.json`, `storage/runtime/angel_hermes_status.json`, logs de `storage/logs/ia/` y manifests de `modules/laboratory/manifests/`.
